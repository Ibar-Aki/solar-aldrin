# v2-modern V2改善提案レポート

## 1. レポート概要

本レポートは、`apps/v2-modern` を対象に、V2 の現状実装・関連ドキュメント・テスト状態を確認したうえで、次に優先すべき改善項目を整理したものです。

結論として、V2 は基盤品質自体は高く、即座に大規模な作り直しが必要な状態ではありません。一方で、現場運用を強く意識すると、以下の 4 項目は早期に手当てしたほうがよいと判断しました。

- 公開リンク配布を前提にした濫用対策の明確化
- 履歴保持ポリシーの一元化と仕様差分の解消
- PWA / オフライン復帰導線の実装
- 業務KPIを取れる可観測性への拡張

2026-05-28 補足: 友人・現場関係者へ LINE 等でURLだけを共有して簡単に使える体験を優先するため、当面は本番APIトークン必須化を採用しません。濫用対策は、IP単位レート制限、AI出力トークン上限、API body上限、チャット履歴件数上限で行います。

## 2. 調査サマリ

今回の確認では、主に以下を対象に調査しました。

- フロントエンド実装: `src/pages`, `src/hooks`, `src/lib`, `src/stores`
- Workers 実装: `workers/index.ts`, `workers/routes`, `workers/lib`
- 主要ドキュメント: `README.md`, `docs/README.md`, `docs/10_planning`, `docs/project/core`
- テスト/品質基盤: `tests`, `package.json`

確認結果の要点は以下です。

- `npm run lint` は成功
- `npm test` は 50 ファイル / 221 テストですべて成功
- 状態管理、Workers API、テスト基盤、JSON回復、Dual Provider 対応はかなり整備済み
- 一方で、公開リンク配布時の濫用対策、保存期間、PWA/オフライン、KPI観測、設計文書の同期は未完成または不整合が残っている

## 3. 現状評価

### 3.1 良い点

- 会話フロー、状態管理、エラー処理、Silent Retry まで含めてフロントの制御がよく整理されている
- Workers 側は CORS、レート制限、認証、Sentry、メトリクスがルーティング単位で分離されている
- テスト範囲が広く、回帰耐性が高い
- PDF、履歴、フィードバック、文脈注入など、Phase 2 の差別化要素が実装されている

### 3.2 課題の傾向

- 「コードがない」のではなく、「本番運用として詰め切れていない」課題が多い
- ドキュメント間の記述差分が増えており、将来の判断コストを上げ始めている
- 現場利用に直結する非機能要件の一部が、実装上はまだ保証されていない

## 4. 最優先改善提案

### 4.1 優先度A: 公開リンク配布を前提に濫用対策を明確化する

#### 現状

- 友人・現場関係者へ LINE 等で URL だけを共有して使える導線を重視する
- 公開リンク配布では `REQUIRE_API_TOKEN=0` / `VITE_REQUIRE_API_TOKEN=0` を維持し、利用者に API トークン入力を求めない
- 認証必須化は、限定配布や組織導入など「利用者がログイン導線を受け入れられる運用」に限定して検討する

#### 問題

- URL だけで使える導線は便利だが、API を無制限に呼べる状態にはしない
- トークン必須化だけで対策すると、LINE で配布してすぐ使える体験を損なう
- 公開リンク配布用の安全境界と、限定運用向けの認証強化を混同すると運用判断がぶれる

#### 改善案

- 公開リンク配布では `RATE_LIMIT_KV` による IP 単位レート制限を必須にする
- AI 出力は `OPENAI_MAX_TOKENS` / `GEMINI_MAX_TOKENS` で上限を維持する
- API body 上限とチャット履歴件数上限で、巨大リクエストによるコスト増を抑える
- 限定運用でだけ `REQUIRE_API_TOKEN=1` / `VITE_REQUIRE_API_TOKEN=1` を使い、トークン UI を有効化する

#### 実装イメージ

- Phase 1: 公開リンク配布の安全境界を実装する
  - 64KB を超える API body を `413 REQUEST_BODY_TOO_LARGE` で拒否する
  - `/api/chat` の履歴件数を 20 件までに制限する
  - レート制限・トークン上限・body上限を運用手順へ明記する
- Phase 2: 限定運用向けの認証を選択式に残す
  - API トークン方式は、公開リンク配布ではなく限定配布時のみ使う
  - 将来の組織導入では Cloudflare Access や短命セッションへ移行できるようにする

#### 効果

- LINE 等で配布してすぐ使える体験を維持できる
- 不正利用やコスト増の主経路を、認証ではなく量的制限で抑えられる
- 将来の限定配布・組織導入にも段階的に接続しやすい

### 4.2 優先度A: 履歴保持ポリシーを一元化し、仕様差分を解消する

#### 現状

- `historyUtils.ts` では `RETENTION_DAYS = 90`, `MAX_SESSIONS = 100`
- ただし保持制御は履歴系ユーティリティ経由でのみ適用される
- `HistoryPage.tsx` は `getAllSessions()` で DB を直接読む
- `db.ts` の保存処理には保持制御がない
- ドキュメント上も保存期間が食い違っている
  - 全体要件では Phase 1-2 のローカル保存は 30 日
  - 機能概要では 90 日または 100 件で自動削除

#### 問題

- 実装上、保持制御が常に発動するとは限らない
- 30日なのか90日なのかが設計上曖昧
- 仕様差分があると、現場説明・監査・今後の実装判断で齟齬が出る

#### 改善案

- 保存期間の正本を 1 つに決める
  - 推奨は「現場要件優先」で Phase 2 は 30 日に統一
- 保持制御を `db.ts` 側へ寄せる
  - 保存時
  - 全件取得時
  - 件数取得時
- UI は保持制御済みの API だけを使う
- エクスポート前通知や削除予定件数表示も将来的に追加する

#### 実装イメージ

- `db.ts` に `applyRetentionPolicy()` を集約
- `saveSession`, `getAllSessions`, `getLatestSession` の入口で適用
- `historyUtils.ts` は保持制御を持たず、検索・整形専用に縮退
- ドキュメントを 30 日基準へ同期

#### 効果

- 仕様と実装のズレが消える
- 履歴関連の不具合や「消える/消えない」の説明コストが下がる
- Phase 3 のサーバー保存移行時にも責務分離しやすい

### 4.3 優先度A: PWA / オフライン復帰導線を V2 で整備する

#### 現状

- 要件では「オフライン時の入力内容保持」が明記されている
- 実装上、状態保持や IndexedDB はあるが、PWA としての構成は未整備
- 調査時点でアプリ配下に manifest / service worker は確認できなかった

#### 問題

- 通信断時に「どこまで保存されるか」「いつ再送されるか」が利用者に見えない
- ホーム画面追加や再訪導線が弱い
- 現場の電波不安定前提に対して、UX がまだ説明不足

#### 改善案

- Web App Manifest を追加し、ホーム画面追加を可能にする
- Service Worker を導入し、静的アセットと直近画面をキャッシュする
- オフライン時は明示バナーを出す
- `/api/chat` 送信失敗時に「下書き保存済み」「通信復帰後に再開してください」を案内する
- セッション再開時に最後の未送信入力や未完了作業を分かりやすく復元する

#### 実装イメージ

- Phase 1: Manifest + インストール導線 + オフラインバナー
- Phase 2: Chat 失敗時の再送キューまたは手動再送導線
- Phase 3: PDF テンプレや履歴一覧のオフライン閲覧最適化

#### 効果

- 現場利用時の信頼感が上がる
- 「アプリが止まった」という印象を減らせる
- 音声が不安定でもテキスト主導で完遂しやすくなる

### 4.4 優先度A: 可観測性を業務KPIレベルへ拡張する

#### 現状

- `metrics.ts` のイベント種別は技術的なものが中心
- 取得できるのは `session_start`, `session_complete`, `input_length`, `chat_error`, `retry_*` など
- これだけでは「何が現場価値に効いたか」を追いづらい

#### 問題

- UI改善や音声改善をしても、業務成果との相関を測りにくい
- どこで離脱しているかが分からない
- 将来的な ROI 説明の根拠が弱い

#### 改善案

- 以下の業務KPIイベントを追加する
  - `work_item_1_completed`
  - `work_item_2_started`
  - `work_item_2_completed`
  - `action_goal_recorded`
  - `pdf_downloaded`
  - `feedback_adopted`
  - `voice_start_failed`
  - `voice_fallback_to_text`
- ダッシュボードで見るべき主要指標を固定する
  - 開始率
  - 完了率
  - 2件目到達率
  - PDF保存率
  - 音声失敗率
  - 手動リトライ率

#### 効果

- 改善施策の優先順位をデータで決められる
- 現場導入時に「便利そう」ではなく「使われている」を示せる
- 将来の Phase 3 投資判断がしやすくなる

## 5. 中優先改善提案

### 5.1 優先度B: 深掘りUXを自由入力一辺倒から改善する

#### 現状

- ロードマップ上でも 5W1H 深掘りや選択式 UI は保留
- 現状でも会話品質は悪くないが、入力負荷はまだ利用者依存が大きい

#### 改善案

- 原因候補チップ、災害結果候補チップ、対策カテゴリ候補を補助 UI として出す
- 音声が不安定な端末では、選択補助を優先表示する
- 「抽象回答が続いたら選択式に切り替える」分岐を入れる

#### 効果

- 曖昧回答を減らしやすい
- 新規利用者でも質を安定させやすい
- 騒音環境や手袋環境での操作負荷が下がる

### 5.2 優先度B: ドキュメントの正本管理を整理する

#### 現状

- `architecture-design.md` は React 18 / OpenAI 単独前提の記述
- `apps/v2-modern/README.md` は React 19 / Gemini 対応
- 保存期間も 30 日と 90 日で揺れている

#### 問題

- 実装判断の前提がファイルごとに違う
- 新しい改善案の議論時に、どの文書を信じるべきかが曖昧

#### 改善案

- V2 の正本を `docs/00_overview/00_Master_Technical_Reference.md` か `docs/10_planning/05_Technical_Spec.md` に寄せる
- 全体設計と V2 実装差分を定期的に同期する
- 「要件」「現行仕様」「将来計画」を混ぜずに分ける

#### 効果

- 変更判断が速くなる
- レビュー時の無駄な往復が減る
- 後続フェーズの設計負債を増やしにくい

## 6. 低優先だが有効な改善

### 6.1 優先度C: エクスポート機能の次段階を先回り設計する

- 現在は CSV / JSON 出力だが、要件上は `.xlsx` や指定期間抽出が将来必要
- Phase 2 のうちにデータ列定義とエクスポート契約を固定しておくと、Phase 3 実装が楽になる

### 6.2 優先度C: 参考情報リンクを運用管理できる構造へ寄せる

- 現在は固定 URL 参照のため、法令改定や資料差し替え時の運用コストが出る
- 定数化または設定化しておくと保守しやすい

## 7. 推奨実施順序

短期で着手するなら、以下の順を推奨します。

1. 認証方式の本番/開発分離
2. 履歴保持ポリシーの一元化
3. PWA/オフライン基盤の導入
4. KPIイベント拡張
5. 深掘り補助UI
6. ドキュメント正本の整理

## 8. 3段階の実行ロードマップ案

### 第1段階: 運用リスク低減

- 本番認証を強化
- 保存期間を統一
- ドキュメントの矛盾を解消

### 第2段階: 現場体験の安定化

- PWA化
- オフライン復帰導線
- 音声失敗時のテキスト誘導強化

### 第3段階: 改善の自走化

- 業務KPI追加
- 分析ダッシュボード整備
- 深掘りUXのABテスト

## 9. まとめ

V2 は、実装品質とテスト品質の観点では十分に次の改善投資へ進める状態です。優先すべきは大規模な再設計ではなく、現場運用に効く非機能領域の仕上げです。

特に、認証、保存期間、オフライン、KPI の 4 点は、機能追加より先に整える価値があります。ここを固めることで、V2 は「動く試作」から「現場に継続導入できる業務システム」へ一段階上げられます。
